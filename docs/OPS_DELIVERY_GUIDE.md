# LiteLLM Gateway 可观测与安全建设 — 交付方案

**交付日期**: 2026-07-07
**适用规模**: 2000+ 员工共享网关
**模块位置**: 仓库 `ops/` 目录（独立部署，不影响网关主链路）

---

## 1. 建设背景：从一次真实事故说起

此前发生的安全事件：**LiteLLM master key 泄露，攻击者用它产生了大量调用费用，直到财务对账时才被发现**。

复盘这次事故，暴露了三个能力缺口：

| 缺口 | 事故中的表现 | 本方案的目标 |
|------|-------------|-------------|
| **发现慢** | 靠账单对账发现，滞后数周 | 泄露的 key 一旦被使用，**5 分钟内告警到飞书** |
| **查不清** | 无法回答"谁用的、从哪来、用了多少" | 分钟级出溯源结果（来源 IP、时段、模型、token 消耗） |
| **止不住** | 滥用速率无上限，损失随时间线性扩大 | WAF 限速封顶滥用速率 + 地理围栏挡掉大部分攻击源 |

方案设计的核心思路：**不是堆监控指标，而是沿着"事故再来一次会怎样"的链路，把每个环节补上**。

## 2. 方案总览：三层防线

```
┌─────────────────────────────────────────────────────────────┐
│  事前收敛（降低被攻击面）                                      │
│  WAF 地理围栏(仅 CN/SG/US) · AWS 托管规则(注入/恶意IP)        │
│  按 API-key 限速 · 管理路径 IP 白名单(开关就绪)               │
├─────────────────────────────────────────────────────────────┤
│  事中发现（分钟级告警 → 飞书）                                 │
│  ★ master key 使用告警（本次事故的靶心）                      │
│  master key 密钥被读取 · GuardDuty 威胁发现 · root 登录       │
│  4XX 撞库信号 · 请求量异常 · NAT 出站流量异常(数据外泄)        │
│  5XX/延迟/容器健康（服务可用性 7 条）                          │
├─────────────────────────────────────────────────────────────┤
│  事后溯源（分钟级取证）                                        │
│  审计数据湖(每笔调用含 key 归因+来源 IP)                       │
│  CloudTrail/Flow Logs Athena 取证表 + 8 条预置溯源 SQL        │
│  QuickSight 看板 3 页(使用总览/安全异常/网络)                  │
└─────────────────────────────────────────────────────────────┘
         告警通道统一: CloudWatch/EventBridge → SNS → Lambda → 飞书(加签)
```

**组件构成**（4 个 CloudFormation 栈，一条命令部署 `ops/deploy-ops.sh`）：

| 栈 | 内容 |
|----|------|
| `litellm-gw-ops-monitoring` | 8 条服务健康/流量告警 + CloudWatch Dashboard + 飞书通知 Lambda |
| `litellm-gw-ops-waf` | WAF WebACL（地理围栏、托管规则、三级限速），已关联 ALB |
| `litellm-gw-ops-security` | 安全事件告警（GuardDuty / 密钥读取 / root 登录 / **master key 使用**） |

## 4. 指标体系：每个指标是什么、为什么、阈值怎么定

### 4.1 阈值方法论（先讲清楚"数字怎么来的"）

本方案使用三种阈值机制，对应三类不同性质的信号：

1. **绊线（阈值=0）**：用于"正常情况下就不该发生"的事件。只要出现即告警，零误报的前提是先把正常业务收敛干净（例如日常流量全部走 virtual key，master key 归零）。
2. **固定阈值（按规模校准）**：用于"有正常噪声，超过量级才异常"的信号。所有数字都按 **2000+ 员工规模**校准过，并且做成参数（`ops/params.env`），上线一周后可按真实基线二次校准。
3. **异常检测带（动态基线）**：用于"没有绝对合理值，偏离自身历史规律才异常"的信号。CloudWatch 机器学习模型持续学习该指标的周期规律（工作日/夜间/周末），实际值超出"预期带"才告警。带宽（标准差倍数）越大越不敏感。

### 4.2 安全类指标（本次建设的重心）

| 告警 | 指标定义 | 为什么选这个指标 | 阈值及依据 |
|------|---------|----------------|-----------|
| ★ **master key 使用** | 审计流水中 `key_alias` 为空的请求数（Sum/5min）。LiteLLM 给 virtual key 打 alias 标签，master key 没有——**alias 为空即 master key** | 事故的靶心信号。攻击者拿泄露的 key 调 API **不会触碰任何 AWS 管理接口**，传统云安全监控全部失明；只有从业务流水本身识别"这笔调用用的是哪把 key"才抓得住 | **0（绊线）**。经验证客户现有流量已全部走 virtual key，master key 用量应恒为零，一动即异常 |
| **master key 密钥被读取** | CloudTrail 中 `GetSecretValue` 命中 `*master-key*` 的事件 | 回答"泄露途径"：如果有人从 AWS 侧窃取密钥，此处留痕并实时告警（正常只有 ECS 部署角色会读） | 事件驱动，无阈值 |
| **Target 4XX 激增** | ALB 后端返回的 4XX 数量（Sum/5min，连续 2 周期）。选 `HTTPCode_Target_4XX` 而非 ELB 自身 4XX——前者才包含 LiteLLM 返回的 401/403/429 | 撞库/枚举 key 的直接信号：攻击者批量试 key 会产生大量 401 | **1000/5min**。2000 人规模下 429（限额）、400（上下文超长）是日常噪声，实测基线定 1000；上线一周后按真实数据回调 |
| **请求量异常** | ALB RequestCount 偏离动态基线（连续 2 周期） | 拿到有效 key 的攻击者不产生 4XX，但总请求量会偏离该时段的历史规律 | **异常检测带，带宽 3**。大规模流量天然波动，带宽 2 实测过敏 |
| **NAT 出站流量异常** | NAT 网关 `BytesOutToDestination`（出站字节数）偏离动态基线（连续 2 周期） | 数据外泄的实时信号：如果内部组件被植入外传数据，出站字节量会突破历史规律 | **异常检测带，带宽 6**。用户爬坡期出站流量增长快，带宽 3 实测误报（正常增长 1.46 倍即触发），调宽至 6 后仍能捕获量级级别的外泄 |
| **GuardDuty 威胁发现** | AWS 威胁情报引擎的发现（severity≥4） | 覆盖挖矿、C2 通信、凭证异常使用等已知威胁模式，与自建告警互补 | severity≥4（Medium 及以上） |
| **root 账户登录** | AWS root 控制台登录事件 | root 登录在日常运维中不应发生 | 事件驱动（绊线性质） |

### 4.3 服务健康类指标（可用性保障）

| 告警 | 指标定义 | 阈值及依据 |
|------|---------|-----------|
| Target 5XX | 后端 5XX 数量 Sum/5min | 25/5min（2000 人规模下零星 5XX 难免，量级异常才告警） |
| p95 延迟 | ALB TargetResponseTime p95，连续 3 周期 | 45 秒（LLM 长上下文首 token 天然偏慢，30s 在大规模下误报） |
| 不健康主机 | ALB 目标组 UnHealthyHostCount，连续 3 分钟 | >0 |
| ECS CPU / 内存 | 服务平均利用率，连续 3 周期 | 85% |
| 运行任务数不足 | RunningTaskCount < 期望值，连续 3 分钟 | <2 |

> 所有阈值均为 `ops/params.env` 中的参数，客户可按自身基线调整后重跑部署脚本生效。

### 4.4 WAF 防护规则（不是指标，但决定了"损失上限"）

| 规则 | 设计 | 为什么这样设计 |
|------|------|--------------|
| 地理围栏 | 仅放行 CN/SG/US | 员工分布之外的来源直接拒绝，砍掉全球扫描流量 |
| **按 API-key 限速** | Authorization 头 / x-api-key 头 各 3000 次/5min | **关键设计**：2000+ 员工共享公司出口 IP，按 IP 限速会误杀整个公司；按 key 聚合才能精准限住"某一把 key 被刷"——正是泄露场景 |
| 按 IP 限速 | 20000 次/5min | DoS 兜底（阈值高于全公司单出口的正常峰值） |
| AWS 托管规则 | Common/KnownBadInputs/IpReputation | 注入攻击、已知恶意 IP。其中 3 条 body 检查规则设为观察模式——AI 编程工具的请求天然包含大 body/代码片段/文件路径，实测会误拦 |
| 管理路径锁定 | `/key /user /team` 等管理 API 仅白名单 IP 可访问 | **开关已就绪**（`ENABLE_ADMIN_LOCKDOWN`），待提供固定运维出口 IP 后启用。启用后即使 master key 再泄露，攻击者也无法调用管理 API 增发 key |

## 5. 核心能力详解：master key 使用告警

这是针对事故靶心新建的能力，值得单独说明其实现与验证。

### 5.1 数据链路

```
每笔 LLM 调用 → LiteLLM 审计流水(DynamoDB)
  → DynamoDB Stream 实时触发 Lambda
    → 解析每笔调用的 key 身份(key_alias/key_hash/team/来源 IP)
      → key_alias 为空(=master key)时输出 CloudWatch 指标 MasterKeyRequests
        → 告警(Sum/5min > 0) → SNS → 飞书
```

延迟构成：流处理批窗口 ≤60 秒 + 告警评估周期 5 分钟 ⇒ **端到端约 1~6 分钟**。

### 5.2 两个关键设计决策

**为什么用"key_alias 为空"作为 master key 的判定？**
LiteLLM 在每笔调用的元数据中记录 `user_api_key_alias`（virtual key 的别名标签）。master key 不是 virtual key，没有 alias。该口径与审计湖、QuickSight 看板完全一致，三处数据可以互相印证。

**归因数据的防伪造加固**
调用元数据中混有用户可控内容（如请求头）。解析器在提取 key 身份前会剥离所有嵌套内容块、只认 LiteLLM 写入的顶层字段——攻击者无法通过构造请求头伪造 key 归因、也无法伪装成 virtual key 逃过 master key 计数（已通过独立安全审查验证此攻击路径不可行）。

### 5.3 端到端验证记录（2026-07-07，生产环境实测）

| 环节 | 结果 |
|------|------|
| 注入一笔 master key 形态的测试流水 | 处理成功 |
| CloudWatch 指标 `MasterKeyRequests` | Sum=1 正常产生 |
| 告警状态翻转 | 约 5 分钟内 OK → ALARM |
| 飞书通知 | 投递成功（HTTP 200） |
| 测试数据清理 | 已从审计湖删除 |
| 期间真实流量 | **零 master key 调用**——现有业务已全部收敛到 virtual key，此告警从交付日起即为零噪声绊线 |

### 5.4 收到该告警怎么办（处置指引）

1. **确认**：登录 QuickSight 看板"安全异常"页，或执行审计湖查询，确认调用的来源 IP、时段、模型与消耗；
2. **判断**：若是内部人员误用 master key → 通知其改用 virtual key；若来源不明 → 按泄露处置；
3. **止损**：立即轮换 master key（Secrets Manager 更新 + ECS 服务滚动重启），泄露 key 即刻失效；
4. **溯源**：执行 `ops/security/queries/01-master-key-reads.sql` 确认 AWS 侧是否有异常密钥读取，结合审计湖流水估算损失。

### 6.1 QuickSight 看板（3 页）

| 页面 | 内容 | 回答的问题 |
|------|------|-----------|
| 使用总览 | 请求量/token 趋势、Top 消耗者（按 key/团队/会话） | 谁在用、用了多少、增长趋势 |

| 网络 | 出站流量 Top 目的地 | 数据流向是否符合预期 |

### 6.2 预置溯源 SQL（8 条，Athena 分钟级出结果）

| 查询 | 用途 |
|------|------|
| 01 master key 读取记录 | 谁从 AWS 侧读过 master key 密钥（泄露途径排查第一步） |
| 02 可疑密钥读取 | 排除正常部署角色后的异常读取 |
| 03 敏感管理 API | 谁调用过增发 key/改配置等管理操作 |
| 04 控制台登录记录 | 登录来源与成败 |
| 05 IAM 密钥生命周期 | 访问密钥的创建/删除轨迹 |
| flow-01 出站流量 Top | 数据外传到哪、多少字节 |
| flow-02 被拒连接 | 内网扫描/异常连接尝试 |
| flow-03 按网卡出站 | 定位是哪个组件在外传 |

## 7. 交付边界与后续建议

已交付并验证的能力如上。以下事项建议纳入下一阶段：

| 优先级 | 事项 | 说明 |
|--------|------|------|
| **P0** | **master key 定期轮换机制** | 当前 master key 永不过期。告警能抓到滥用，但泄露的 key 本身仍永久有效——轮换机制是止损的最后一环 |
| P1 | 成本告警（AWS Budgets / Cost Anomaly Detection） | 把"对账发现"这条兜底通道也自动化到 24 小时级 |
| P1 | LiteLLM 按 key/团队预算硬上限（max_budget） | 即使完全未被发现，单 key 损失也有天花板 |
| P1 | 管理路径锁定启用 | 待提供固定运维出口 IP，改一个参数即生效 |
| P2 | 上线一周后阈值校准 | 4XX/请求量等固定阈值按真实基线回调，参数化改动已就绪 |
| P2 | 可靠性告警补全 | RDS/Redis/证书到期等（当前聚焦安全与网关本体） |

## 附录 B：现场演示路径（约 10 分钟）

1. **看板**（2 min）：打开 QuickSight `litellm-gw-dashboard`，展示使用总览与 master key/virtual key 占比；
2. **告警实弹**（5 min）：向流处理 Lambda 注入一笔 master key 形态的测试流水（方法同 5.3 验证），现场等待飞书群收到 `[ALARM] litellm-gw-ops-master-key-usage`；

4. 演示后清理测试流水（删除审计桶对应对象），告警约 25 分钟后自动恢复。
